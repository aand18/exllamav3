## Measurement conventions

- **Screen at 131072, confirm at 262144.** A screening pass is ~10 min, a confirmation pass ~20-25
  min (load 1.5 min + warmup + bands). A decision is 4 passes (ABBA) unless stated otherwise.
- **ABBA on every comparison:** reference, variant, variant, reference, in one window. A ratio is
  only valid against a reference measured in that same window (drift ~10%/session, #157).
- **Acceptance:** median of the two per-band ratios must exceed the band's own boot-to-boot spread
  (measured in Task 4). No claim below the spread; no claim from absolute numbers across sessions.
- **Metrics:** pp = the `Length` bands of `perf.py`; tg = the `Context` rows at `S=1`; the `S=2..4`
  rows are the cost of an MTP verification step, not an acceptance rate. MTP acceptance is measured
  in Task 11 with `eval/spec_decode.py`.
- Every pass records min-free VRAM, min-free RAM and peak process RAM (§ `FLOORS`).

## The harness (committed in `bench/windows/`, validated in Task 2)

Everything runs through the scripts in `bench/windows/` — committed, documented in
`bench/windows/README.md`, deployed to the box with `bench/windows/deploy.sh`. Never write a new
script for a benchmark: add a regime to `run_pass.ps1`.

| Script | Purpose |
|---|---|
| `watch.ps1` | samples VRAM/RAM every 1 s, writes `results/watch-<tag>.csv`, kills the process tree and writes `results/BREACH-<tag>.txt` when 200 MB VRAM / 2048 MB RAM free is crossed |
| `run_pass.ps1` | one `perf.py` pass in a named regime, under the watcher, parsed into `results/{passes,pp,tg}.csv`, prints the `HARNESS/PASS/FLOORS/PP/TG_S1` block |
| `run_build.ps1` | one wheel build, under the watcher, records the wheel and its size in `results/builds.csv` |
| `deploy.sh` | copies the three scripts plus `eval/perf.py` to `C:/Users/yoho/Downloads/tabbyAPI/_agent/v164/` |

`bench/windows/legacy/` holds the v1.4.9/v1.5.4 scripts that produced the earlier numbers; they are
superseded, and their README says which result came from which. `build_wheel.bat` there is still the
authoritative build recipe that `run_build.ps1` wraps.

Invocation from the WSL shell (Windows path, `-File`):

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File \
  "C:\Users\yoho\Downloads\tabbyAPI\_agent\v164\run_pass.ps1" \
  -Tag <tag> -MaxLength 131072 [-Env "K=V,K=V"] [-Unset "K,K"] \
  [-Threads 16] [-Split 360] [-Extra "-cq 4,4"] [-NoSpecDec] [-Prof]
```

- `-Env` overrides the regime's environment; `-Unset` removes inherited variables.
- `-Threads` / `-Split` replace the regime's `-mct` / `-mcs`, the two numbers that change most
  often; both are recorded as columns in `passes.csv`.
- `-Extra` appends raw `perf.py` flags, e.g. `-Extra "-cq 4,4"` (quantized cache) or
  `-Extra "-rcs 8"` (recurrent checkpoint budget, GB). The exact args of every pass are recorded in
  `passes.csv` and in the log header, so no report has to reconstruct them.

`perf.py` in that
directory is a byte-identical copy of `eval/perf.py` from tree `v1.6.4`
(sha256 `246e721a62d7c5238de4b7296adb0b26cd9f42a734b9f648436b35b9b6a29e04`), which is also
byte-identical to the 1.5.4 copy, and it imports the **installed** engine.

The `production` regime inside `run_pass.ps1` is: model 2.05bpw, `-mcs 360 -mct 16 -cs 262144
-chunk_size 4096 -ambs 2`, `-sd` (decode at S=1..4), `EXL3_MOE_MEMOPS=0`, `EXL3_MOE_CPU_PIN=1`,
`EXL3_MOE_CPU_SWIZZLE=1`; profilers off. **Nothing else is set**, on purpose — see Task 6.
